# Планирование: анализ, идентификация проблем и поиск решений

## Проблемные места

### Технические

- Долгие расчёты стоимости в MES (до 30 мин).
- Один инстанс MES, CRM, магазина — нет масштабирования.
- Медленный UI MES — проблемы на уровне БД и API.
- Одна БД без реплик — ограничение производительности.
- Потеря сообщений между MES <-> CRM через RabbitMQ.
- Отсутствие retry, idempotency, dead-letter queues.
- Нет SLA и rate limiting на API.
- API-партнёры перегружают MES расчётами.
- MES совмещает тяжёлые вычисления и пользовательский UI.

### Процессные

- Один QA без автоматизации → задержки релизов.
- Нет нагрузочного тестирования.
- Нет мониторинга очередей, API, времени расчётов.

### Командные

- C# разработчик всего один → MES
- Слабая экспертиза по React → MES фронтенд плохо поддерживается.

### Бизнес

- Неконтролируемый рост заказов.
- Потери клиентов из-за просрочек.
- Низкая прозрачность сроков обработки заказов.

## Инициативы для устранения нежелательных ситуаций

### Архитектура

1. Выделить сервис расчёта стоимости + worker-pool.
2. Rate limiting + квоты + SLA на API.
3. Кэширование результатов.
4. Масштабирование сервисов.
5. Оптимизация БД.
6. Read-replicas.

### Интеграции

1. Надёжные очереди (retry, DLQ, idempotency).
2. Event-driven архитектура.

### UX и производительность

1. Оптимизация первой страницы MES.
2. Push-обновления статусов.
3. Справедливая очередь для операторов.

### Процессы

1. Автотесты.
2. Улучшенный CI/CD.
3. Нагрузочные тесты.
4. Мониторинг и алертинг.

### Команда

1. Найм SRE.
2. Найм C# разработчиков.
3. Найм backend для API.
4. Развитие QA-автоматизации.

### Бизнес

1. Асинхронная модель расчёта стоимости.
2. Прозрачные сроки.
3. Приоритизация B2C.
4. SLA для партнёров.

## Приоритет

1. Вынести расчёт стоимости в отдельный сервис (Cost Calculation Service)

    Это снимает корень всех проблем:
    - убирает CPU-нагрузку с MES,
    - ускоряет UI,
    - уменьшает задержки,
    - позволяет масштабировать расчёты горизонтально,
    - снижает задержки обработки заказов.

2. Ввести rate limiting, квоты и очереди для партнёрского API

    Иначе любой партнёр может «положить» сервис.

3. Добавить retry / idempotency / DLQ в RabbitMQ между MES и CRM

    Гарантирует отсутствие потерянных заказов.

4. Горизонтальное масштабирование MES + CRM + Online Store

    Иначе при увеличении нагрузки в 2 раза система упадёт.

5. Оптимизация первых страниц MES (запросы, индексы, отдельный lightweight endpoint)

    Прямое влияние на работу операторов + KPI вознаграждений.

6. Мониторинг и алертинг (RabbitMQ, calculation time, API errors)

    Позволит реагировать на проблемы до того, как их заметят пользователи.

## Целевая архитектура

**Главная цель ближайших 6 месяцев** — превратить монолитный MES в лёгкий сервис UI + orchestration, вынеся вычисления в отдельный scalable compute-слой и введя контроль нагрузки.

**Три ключевых инициативы:**

1. **Создать отдельный сервис расчёта стоимости + очередь задач.**
2. **Добавить rate limiting и квоты для партнёрского API.**
3. **Добавить retry/idempotency/DLQ для RabbitMQ сообщений.**

После выполнения этих трёх пунктов:

- система перестанет терять заказы,
- перестанет зависать,
- станет масштабируемой,
- операторы перестанут жаловаться,
- партнёры снова станут довольны.
