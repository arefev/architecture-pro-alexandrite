# Выбор и настройка мониторинга в системе

## Мотивация

В текущей ситуации есть несколько критичных факторов:

* растущая нагрузка каждый месяц;
* задержки в расчётах стоимости;
* потерянные сообщения между MES и CRM;
* деградация скорости MES;
* нестабильный API для партнёров;
* отсутствие понимания, когда и почему система «ложится».

Без мониторинга команда фактически работает «вслепую».

### Что даёт мониторинг компании

* Раннее обнаружение проблем — до того, как клиенты пожаловались
* Прозрачность — понятно, где узкое место
* Понимание реальной нагрузки и прогнозирование роста
* Быстрее искать и устранять причины сбоев
* Объективная оценка качества работы команды
* Основа для автоматического масштабирования
* Прозрачность для партнёров (SLA и отчёты)

## Выбор подхода к мониторингу

| Зона системы                               | Подход               | Цель                                   |
| ------------------------------------------ | -------------------- | -------------------------------------- |
| Фронтовые сценарии и пользовательские флоу | **4 Golden Signals** | Качество работы и UX                   |
| API, внутренние микросервисы               | **RED**              | SLA сервисов, скорость и ошибки        |
| Базы данных, очереди, кэш, инфраструктура  | **USE**              | Нагрузка, ресурсы, стабильность железа |

## Какие метрики будем использовать

## RabbitMQ

### Number of dead-letter-exchange letters in RabbitMQ

**Зачем:**
DLQ — прямой индикатор ошибок бизнес-логики, отказов потребителей, неверных сообщений от API партнёров.
Рост DLQ = увеличиваются пропущенные заказы => причина сбоев заказов.

**Ярлыки:**

* `queue`
* `reason` (expired, rejected, processing_error)
* `producer_service`
* `consumer_service`

---

### Number of messages in flight in RabbitMQ

**Зачем:**
Показывает нагрузку обработки заказов.
Если растёт без падения — потребители перегружены => задержки расчёта цен => задержки заказов.

**Ярлыки:**

* `queue`
* `consumer_service`

## API (интернет-магазин, CRM, MES)

### Number of requests (RPS) for shop / CRM / MES API

**Зачем:**
Понимание нагрузки, аномалий, DDoS, ошибки партнёров API.
Важно при росте заказов.

**Ярлыки:**

* `endpoint`
* `method`
* `status_code_class` (2xx, 4xx, 5xx)

---

### Number of requests (RPS) per user (shop / CRM / MES)

**Зачем:**
Нужно для:

* детекции злоупотребления API партнёрами,
* выявления «шумных» интеграций,
* анализа поведения операторов MES.

**Ярлыки:**

* `user_id`
* `user_type` (shop_user, partner, operator, manager)
* `endpoint`

---

### Latency (response time) for shop / CRM / MES API

**Зачем:**
Главный сигнал деградации.
Рост latency в MES напрямую объясняет жалобы операторов.

**Ярлыки:**

* `endpoint`
* `method`
* `quantile` (p50, p90, p95, p99)

---

### Number of HTTP 500 for shop / CRM / MES API

**Зачем:**
Ошибка 500 — проблема сервиса, а не клиента.
Критично для репутации и партнёрских API.

**Ярлыки:**

* `endpoint`
* `method`
* `error_type` (exception_name)
* `service`

## Number of simultaneous sessions (shop / CRM / MES API)

**Зачем:**
Контроль реального числа активных пользователей.
Для MES помогает видеть пики нагрузки операторов.

**Ярлыки:**

* `client_type`
* `platform` (web/api/mobile)

## Производительность серверов (USE)

### CPU% для shop API, CRM API, MES API

**Зачем:**
Рост CPU почти всегда коррелирует с ростом latency.
Показывает, когда сервис нужно масштабировать.

**Ярлыки:**

* `instance`
* `service`

---

### Memory utilisation для shop API, CRM API, MES API

**Зачем:**
Операторы жалуются на медленный MES => возможны утечки памяти.
Нужно для диагностирования проблем GC.

**Ярлыки:**

* `instance`
* `service`

---

### Memory utilisation for shop DB / MES DB

**Зачем:**
Если БД начинает троттлить — все API, связанные с заказами, тормозят.

**Ярлыки:**

* `db_instance`

---

### Number of DB connections (shop / MES DB)

**Зачем:**
Утечка коннекшенов = API зависает или падает.
Особенно важно при росте заказов.

**Ярлыки:**

* `db_instance`
* `service` (кто открыл соединение)

---

### Size of DB (shop / MES)

**Зачем:**
Контроль роста данных, чтобы не словить внезапный OOM и остановку сервиса.
Особенно важно для MES, где растут 3D-модели.

**Ярлыки:**

* `db_instance`
* `table` (опционально)

## Хранилища и трафик

### Size of S3 storage

**Зачем:**
Хранятся 3D-модели => это расходы.
При росте количества партнёров нагрузка увеличивается.

**Ярлыки:**

* `bucket`
* `file_type` (3d_model, preview, other)

---

### Network traffic: Kb transferred / received (shop / CRM / MES API)

**Зачем:**
Позволяет:

* отлавливать скачки,
* находить крупные ответы,
* диагностировать проблемы интеграций.

**Ярлыки:**

* `service`
* `endpoint`
* `direction` (sent/received)

## План действий

### Базовая инфраструктура мониторинга

1. Создать инстанс time-series базы данных (Prometheus или VictoriaMetrics).
2. Развернуть систему визуализации метрик (Grafana).
3. Настроить хранение метрик и ретеншен-политику (краткосрочная и долгосрочная).
4. Настроить high-availability схему мониторинга (репликация Prometheus или кластер VictoriaMetrics).

### Сбор метрик со всех систем

1. Интегрировать интернет-магазин (Java Spring Boot) с Prometheus Exporter.
2. Интегрировать CRM (Java + Vue) с Prometheus Exporter.
3. Интегрировать MES (C# + React) с Prometheus Exporter.
4. Подключить метрики RabbitMQ.
5. Настроить сбор метрик с S3.

### Мониторинг очередей RabbitMQ

1. Настроить мониторинг DLQ очередей.
2. Добавить метрику messages_in_flight.
3. Добавить метрику времени обработки сообщений consumer-ами.
4. Настроить alerting на рост очередей и обработку дольше нормы.

### Мониторинг производительности API

1. Добавить метрики по RPS для shop/CRM/MES.
2. Добавить сбор latency с разбиением по квантилям.
3. Настроить метрики ошибок (4xx, 5xx).
4. Добавить подсчёт user-specific RPS (для партнёрского API).
5. Добавить трекинг числа одновременных пользовательских сессий.

### Мониторинг баз данных

1. Подключить DB exporters.
2. Собирать метрики памяти БД, размера БД и таблиц.
3. Собирать метрики количества соединений с БД.
4. Настроить alerting на утечки соединений и высокую нагрузку.

### Мониторинг инфраструктуры

1. Настроить мониторинг CPU, RAM, диск, сеть.
2. Настроить мониторинг количества открытых файлов/сокетов.
3. Добавить мониторинг уровня логов.

### Настройка дашбордов

1. Создать дашборд для интернет-магазина (RED-модель).
2. Создать дашборд для CRM (RED-модель).
3. Создать дашборд для MES (RED-модель, включая расчёт стоимости).
4. Создать RabbitMQ дашборд (USE-модель для очередей).
5. Создать дашборд БД (USE: utilization, saturation, errors).
6. Создать бизнес-дашборд "Состояние заказов" (4 Golden Signals).
