# Архитектурное решение по трейсингу

## Где заказ может «сломаться» или зависнуть в системе

### Точки ошибок в Shop API (точка входа заказа)

Заказ может зависнуть при:

* создании заказа (валидация, бизнес-логика)
* записи данных в Shop DB
* отправке сообщения в RabbitMQ (publish error)
* отсутствии подтверждения о доставке сообщения
* тайм-ауте вызова CRM/MES

### Точки ошибок в RabbitMQ

Типовые сценарии зависания:

* сообщение **попало в очередь, но не обрабатывается**
* **зависло у консьюмера** (consumer lag)
* слишком много ретраев
* дублирование сообщений
* сообщение вообще **не дошло** до очереди

### Точки ошибок в CRM API

Заказ может «сломаться» при:

* CRM вернула 500/400
* CRM не отвечает
* CRM приняла заказ, но не обновила его статус
* CRM не отправляет ответ в Shop API / MES
* ошибка синхронизации с CRM DB

### Точки ошибок в MES API

Зависания возникают, когда:

* MES не принял заказ (валидация, ошибка данных)
* MES API недоступен
* внутренняя задача MES зависла в очереди обработки
* статус заказа в MES не обновился
* ошибка записи в MES DB

### Точки ошибок в базах данных**

* медленные запросы (latency spikes)
* deadlock
* неуспешная транзакция
* неконсистентность данных
* неверно записанный статус
* отсутствие записи в истории изменений

### Покрыть трейсингом следующие блоки

* Shop API
* CRM API
* MES API
* Все очереди RabbitMQ
* Все консьюмеры RabbitMQ
* Shop, CRM DB
* MES DB
* S3

## Какие данные должны попадать в трейсинг

Ниже — полный и практический перечень данных, который позволит:

* восстановить путь заказа
* найти точку, где он завис
* увидеть все ошибки
* понять последовательность событий

### Идентификаторы (обязательные)

| Поле                | Назначение                             |
| ------------------- | -------------------------------------- |
| **trace_id**        | Общая цепочка всех операций заказа     |
| **span_id**         | Уникальный участок работы сервиса      |
| **parent_span_id**  | Иерархия вызовов                       |
| **order_id**        | Главный бизнес-идентификатор           |
| **message_id**      | Идентификатор сообщения RabbitMQ       |
| **correlation_id**  | Связь HTTP <=> MQ <=> сервисы              |
| **user_session_id** | Для анализа пользовательских сценариев |

### Данные о заказе по этапам

* текущий статус
* предыдущий статус
* бизнес-операция: create / update / pay / ship / cancel
* шаг процесса:

  * shop_received
  * crm_received
  * mes_received
  * mes_completed
  * crm_completed
* timestamp каждого шага

### Данные по HTTP-запросам и сервисам

| Метрика                            | Зачем                                    |
| ---------------------------------- | ---------------------------------------- |
| URL                                | понять, какой endpoint обрабатывал заказ |
| метод                              | POST/PUT если создание/обновление        |
| HTTP-код                           | ошибки 4xx/5xx                           |
| latency                            | короткие/долгие шаги                     |
| request payload hash               | контроль целостности                     |
| response payload hash              | реакция сервисов                         |
| headers (trace-id, correlation-id) | связь сервисов                           |

### Данные RabbitMQ

Полный набор для диагностики зависания сообщений:

* exchange
* routing_key
* queue_name
* consumer_tag
* message_id
* correlation_id
* retry_count
* dlx_reason
* dlx_timestamp
* time_in_queue (latency)
* delivery_tag
* ack/nack status

### Данные БД и транзакций

* query
* latency
* количество затронутых строк
* тип операции (insert/update)
* ошибка транзакции
* deadlock detection
* row_version / revision

Позволяет понять, что заказ не обновился в БД вовремя.

### Метаданные окружения

Для точной диагностики:

* service_name
* service_version
* instance_id (pod ID / container ID)
* environment (prod/staging/test)
* hostname

## Мотивация

У компании Александрит ключевая проблема:
**заказы часто зависают или оказываются в непонятном состоянии**, и никто не может быстро понять:

* что происходило с заказом;
* где он сейчас находится;
* какой сервис его обработал/не обработал;
* отправилось ли сообщение в очередь;
* обработался ли callback;
* почему статус не обновился в CRM или MES.

Сейчас поиск проблемы занимает часы или дни, потому что путь заказа распределён между:

* интернет-магазином,
* CRM,
* MES,
* очередями,
* воркерами,
* БД.

Без трейсинга это выглядит как «чёрный ящик»: команда видит только крайние точки («заказ создан / заказ не обработался»), но не знает, что было между ними.

---

### Что даст компании внедрение трейсинга

* Прозрачность жизненного цикла заказа
* Быстрое нахождение точки отказа
* Значительное снижение количества зависших заказов
* Повышение доверия клиентов и сокращение SLA-нарушений
* Уменьшение стоимости поддержки

### Технические и бизнес-метрики, на которые влияет трейсинг

* MTTR — среднее время восстановления (Mean Time To Recovery)
* Количество потерянных/зависших заказов
* SLA обработки заказа - процент заказов, прошедших процесс в пределах нормы
* Количество ошибок в интеграциях (HTTP 5xx, DLX, nack)

## Компромиссы

### Не принесёт пользы

* сервис не влияет на жизненный цикл заказа,
* система полностью внешняя/проприетарная,
* компонент слишком низкоуровневый.

### Пока невозможен

* нет единого trace-context propagation,
* шина сообщений не передаёт trace-id,
* используется закрытая middleware без расширений.

### Слишком дорого

* компонент легаси и требует масштабной переработки,
* внешние системы требуют покупки дорогих доработок,
* BPM/оркестраторы не поддерживают плагины под OTel.

## Безопасность

### Корпоративная аутентификация (SSO)

* Использование SSO на базе **Azure AD / Keycloak / Okta / LDAP** — только сотрудники с валидными корпоративными учётными записями смогут войти.
* Поддержка **MFA** для чувствительных ролей (поддержка, DevOps, админы).

### Ролевой доступ (RBAC)

Гранулярные роли:

* **Support:** чтение трейсов, поиск заказов.
* **DevOps / SRE:** администрирование OTel collector’ов, настройка экспортеров.
* **Developers:** доступ только к своим сервисам.
* **Security:** аудит действий пользователей.

**Запрещено по умолчанию:**

* скачивание необработанных логов,
* доступ в write-mode,
* удаление или маскирование трейсов.

### Ограничение доступа по сетевым зонам (Network Segmentation)

* OpenTelemetry Collector и backend observability (Jaeger / Tempo / Zipkin / Grafana Cloud) — **в отдельном выделенном сегменте**.
* Доступ к системе только из **административной подсети или через VPN**.
* Для внутренних сервисов — Zero Trust policy:
  каждый сервис должен аутентифицироваться с помощью service account/token.

### Безопасность данных в коллекторах и на транспортном уровне**

TLS везде

* TLS между сервисами и OpenTelemetry Collector.
* TLS между коллектором и хранилищем трейсинга.
* Сертификаты — в Vault или KMS.

### Маскирование чувствительных данных

Уровни маскирования:

* PII (телефоны, e-mail, паспортные данные заказчиков) — в трейсы не попадают.
* Возможные секреты (Authorization header, JWT) — автоматически скрываются.
* Значения payload из CRM/MES редактируются через OTel Processor (attributes processor).
