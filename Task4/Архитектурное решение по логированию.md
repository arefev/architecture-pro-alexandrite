## Список необходимых логов уровня INFO

INFO-логи должны отражать **основные бизнес-события**, то есть то, что позволяет понять, что происходит с заказом и на каком этапе.

Ниже — единый перечень для всех систем.

### Shop API (интернет-магазин)

**1. Создание заказа**

* время
* order_id
* customer_id
* сумма
* источник (web/mobile)
* trace_id

**2. Изменение статуса заказа**

* order_id
* old_status → new_status
* причина (если есть)
* actor (system/user/store)

**3. Отправка заказа в RabbitMQ**

* exchange
* routing_key
* order_id
* trace_id
* размер payload

**4. Получение ответа от CRM/MES**

* order_id
* новый статус
* response_time

**5. Ошибка валидации или бизнес-логики (но не техническая)**

* order_id
* причина
* user_id

### CRM

**1. Приём заказа от Shop API**

* order_id
* source_system
* trace_id

**2. Изменение статуса в CRM**

* old_status → new_status
* инициатор (system/operator)

**3. Отправка задания в MES**

* order_id
* type (pack, ship, produce)

**4. Таймауты интеграций, превышающие допустимые SLA**

* order_id
* target_system
* duration_ms

### MES

**1. Начало обработки заказа**

* order_id
* operation (production, picking, packing)
* operator_id

**2. Завершение операции**

* order_id
* operation
* result (success/fail)

**3. Отправка статуса обратно в CRM**

* order_id
* new_status
* trace_id

### RabbitMQ

**1. Публикация сообщения**

* exchange
* routing_key
* size
* message_id
* correlation_id
* trace_id

**2. Получение сообщения сервисом**

* queue
* consumer
* ack/nack

**3. Переход сообщения в Dead Letter Queue**

* message_id
* original_exchange
* reason

## Другие уровни логирования

### DEBUG – только в интеграционных и технических участках

Примеры:

* параметры вызова внешнего API (без персональных данных),
* детали обработки сообщений в RabbitMQ,
* параметры retry/backoff.

DEBUG включается:

* только в тестовой среде,
* в проде — по времени (feature-flag на 15–30 минут).

### WARN — когда всё ещё работает, но поведение ненормальное

Примеры:

* слишком долгий ответ MES (> SLA),
* очередь RabbitMQ превышает порог,
* подозрение на повторные сообщения (duplicate)
* деградация частичного функционала.

### ERROR — для неисправимых технических ошибок

Примеры:

* CRM недоступна, запросы падают,
* невозможно записать заказ в БД,
* сообщение не удалось обработать и оно уходит в DLQ.

### FATAL / CRITICAL — редко, только если сервис полностью недоступен

Примеры:

* база данных полностью отвалилась,
* Shop API не может подняться,
* критический сбой кластера сообщений.

## Мотивация

Сейчас команда сталкивается с ключевыми проблемами:

* заказы «зависят» между сервисами;
* сообщения в очередях RabbitMQ теряются;
* CRM, MES и интернет-магазин не синхронизированы;
* операторы и клиенты не понимают, **где находится заказ**;
* компания теряет контракты и получает жалобы.

Всё это — следствие отсутствия **централизованного логирования**, которое должно:

### Давать прозрачность жизни заказа (end-to-end)

Без логов невозможно понять:

* попало ли сообщение в RabbitMQ;
* кто обработал заказ;
* почему заказ завис в CRM;
* получил ли MES уведомление;
* был ли ответ отправлен обратно.

Логирование делает каждый шаг заказов **прозрачным и проверяемым**.

### Помогать находить технические дефекты до того, как они повлияют на клиентов

Сейчас сбои становятся известны только:

* когда клиент звонит,
* или когда оператор жалуется на тормоза MES.

Логирование позволит обнаруживать проблему в момент её возникновения:

* ошибки интеграций,
* сбои RabbitMQ,
* таймауты MES,
* падения API.

### Ускорить расследование инцидентов

Сегодня поиск причины занимает **часы или дни**.

Централизованный логинг позволяет:

* находить ошибку **за минуты**,
* работать через единый инструмент (Grafana, Kibana, Loki, ELK).

### Метрики, на которые влияет внедрение логирования

* Mean Time To Detect (MTTD)
* Mean Time To Repair (MTTR)
* Количество неуспешных интеграций между системами
* SLA доставки / SLA обновления статусов
* LTV клиентов и retention партнёров по API
* Количество отмен заказов из-за задержек

### В каких системах логирование и трейсинг нужно внедрять в первую очередь

MES (C#) — первый приоритет. Почему:

* именно MES загружен больше всех;
* именно MES «висит» на детализированных 3D-моделях;
* операторы жалуются на долгие загрузки;
* MES отправляет критические статусы:
  **MANUFACTURING_STARTED => MANUFACTURING_COMPLETED => SHIPPED**.

Если MES не отправил статус => заказ «умирает».

## Предлагаемое решение

### Технологический стек

**1. OpenTelemetry SDK**

Используется в сервисах:

* Shop API (Java)
* CRM (Java)
* MES (C#)
* RabbitMQ consumers
* Сервисы интеграций

Зачем:

* все логи структурированы в stdout
* автоматическая передача trace_id в каждый лог
* единый формат для OpenSearch

**2. Локальная запись логов**

Каждый сервис пишет структурированные логи в stdout.

**3. Filebeat**

Устанавливается:

* на каждый pod в Kubernetes (DaemonSet)

Функции:

* собирает логи с сервисов
* парсит JSON
* добавляет метаданные (hostname, service name, env)
* отправляет в OpenSearch bulk-запросами

**4. OpenSearch**

Хранилище логов:

* распределённое
* отказоустойчивое
* масштабируемое
* поддерживает ролевая модель (RBAC)
* обеспечивает быстрый поиск

Используем:

* OpenSearch для данных
* Index Templates для разных типов логов

**5. OpenSearch Dashboards**

Для просмотра логов:

* разработчиками
* DevOps
* support-командой

Функции:

* поиск по trace_id / order_id
* быстрые дешборды по ошибкам
* alerts


### Политика безопасности логов

Цель — защитить персональные данные и снизить риск утечек.

**Что запрещено логировать**

* ФИО
* телефоны
* email
* адрес доставки
* банковские данные
* JWT токены / session id
* содержимое файлов и 3D-моделей
* сырые запросы пользователей

**Санитаризация логов**

### Управление доступом

#### Полный доступ к логам

* DevOps
* Архитектор
* Senior-разработчики

#### Ограниченный доступ

* Поддержка
* Менеджеры CRM
* MES-операторы
  Доступ ограничен по:
* индексам
* полям JSON (через Field-level Security)
* маскированию данных в Dashboards

#### Доступ запрещён

* Маркетинг
* Продакт
* Продажи

Все доступы через SSO (LDAP/SAML).

#### Безопасная передача

* Filebeat -> OpenSearch только по TLS
* API-ключи хранятся в Vault или KMS
* сеть — только внутри приватного VPC

### Политика хранения логов**

Используем **Index Lifecycle Management (ILM)**.

---

### Business Logs (основные)

* статус заказа
* бизнес-операции CRM
* операции MES

**Хранение:** 90 дней
**Индекс:** `alexandrite-business-*`
**Шардирование:** 1–3 шардов
**Replica:** 1

---

### Error Logs (ошибки сервисов)

Хранение: **30 дней**
Индекс: `alexandrite-errors-*`

---

### Debug Logs

Хранение: **7 дней**
Включаются только по флагу.

---

### Инфраструктурные логи

Хранение: **14 дней**
Индекс: `alexandrite-infra-*`

---

### Объём индексов

| Система        | Индекс    | Причина                           |
| -------------- | --------- | --------------------------------- |
| Shop           | отдельный | много логов                       |
| CRM            | отдельный | бизнес-операции                   |
| MES            | отдельный | важные производственные изменения |
| RabbitMQ       | отдельный | критично для расследований        |
| Инфраструктура | общий     | низкий объём                      |

Итого: **5–6 индексов в OpenSearch**.

## Мероприятия для превращения системы сбора логов в систему анализа логов

### Настройка алертинга (Alerting)

В **OpenSearch Dashboards** есть встроенный механизм Alerting. Его нужно включить и настроить.

### Поиск аномалий (Anomaly Detection)

OpenSearch имеет плагин **Anomaly Detection**, который использует ML-модели для выявления отклонений.
