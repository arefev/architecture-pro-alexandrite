# Архитектурное решение по кешированию

## Мотивация

Из описания видно:

### Система тяжёлая на **расчёт стоимости 3D-моделей** (2–3 мин, до 30 мин)

Это главный bottleneck.

### MES вызывает API «Александрита» для расчёта стоимости

Партнёры B2B начали массово вызывать API => нагрузка резко выросла.

### CRM и MES нагружены из-за большого количества заказов

### На дашбордах MES долго грузится список заказов

Причина: тяжёлые запросы к БД, много данных.

### RabbitMQ используется для обмена событиями → иногда сообщения теряются или задерживаются

### Данные заказов изменяются не так часто, как они читаются

У CRМ / MES частые GET-запросы.

## Кеширование результатов расчёта стоимости 3D-модели в MES (самое важное)

**Почему это нужно:**

* расчёт занимает 2–30 минут
* нагрузка растёт с партнёрским API
* одинаковые модели/заказы могут пересчитываться
* можно избежать повторного 30-минутного расчёта

**Что кешируется:**

* результат расчёта `price`
* время обработки
* параметры материала, размера и т.д.
* хеш 3D-модели (по файлу / содержимому)

**Где хранить:**

* Redis
* TTL: 24–72 часа

**Что это даст:**

* уменьшит нагрузку MES в 10–50 раз
* устранит задержки расчёта
* партнёры API перестанут «заваливать» систему


## Кэширование 3D-моделей (S3 → локальный CDN-кеш)

**Почему:**

* каждый расчёт требует загрузки файла
* 3D-модели могут быть большими (много полигонов)
* один и тот же файл может быть использован в нескольких пересчётах
* уменьшает I/O в S3 на 30–80%

**Как кешировать:**

* Nginx + proxy_cache
* CDN (если компания готова)

**TTL: 7 дней**

## Кеширование списка заказов для MES операторов

Операторы жалуются, что:

* «первая страница MES загружается долго»
* «нужны самые свежие заказы»

Но данные о заказах:

* чаще читаются
* реже меняются

**Решение для кеширования:**

* Redis Sorted Set: хранить 200–500 последних заказов
* обновлять при поступлении новых сообщений RabbitMQ
* инвалидация при изменении статуса

**Что даст:**

* ускорение загрузки дашборда в 5–20 раз
* снижение нагрузки на MES DB

## Кеширование справочных данных

Например:

* списки материалов
* каталоги готовых шаблонов
* данные о доставке
* настройки тарифов
* возможные статусы

Эти данные:

* редко меняются
* часто запрашиваются

TTL: несколько суток
Тип: read-through cache

## Клиентское или серверное кеширование?

Клиентское кеширование (на уровне браузера) — *НЕ подходит*

Причины:

**1. Данные зависят от статуса заказа**

Статусы быстро меняются → браузер может показать устаревшие данные (очень опасно).

**2. B2B API — не клиент в браузере**

Партнёры используют серверы → браузерное кеширование не применяется.

**3. CRM и MES — SPA-приложения операторов**

Кеширование в браузере увеличивает риск несогласованности данных:

* оператор видит устаревший список заказов,
* пропускает новый заказ,
* нарушает SLA,
* компания теряет деньги.

**4. Для 3D-моделей браузерное кеширование не решает нагрузку S3 => MES**

Основная боль — на backend, а не на фронтенде.

**Вывод:** клиентское кеширование может использоваться только для статики (JS/CSS), но не для бизнес-данных.

---

### Правильный выбор — серверное кеширование

Это решает реальные проблемы компании:

* кеширование результатов расчёта стоимости
* кеширование 3D-моделей
* кеширование списка заказов на первой странице MES
* кеширование справочников

Используем Redis как основной элемент кэш-слоя.

## Паттерны кеширования: какой и где применять

### Cache-Aside (самый универсальный)

Где используется:

* MES — первая страница заказов (операторы)
* CRM — справочные данные
* Shop API — справочники, каталоги, редко меняющиеся данные

Почему выбрать Cache-Aside:

* данные читаются намного чаще, чем обновляются
* источник истины — база данных
* при инвалидации достаточно удалить ключ в Redis
* легко интегрируется без переписывания логики систем
* минимальный риск порчи данных

Почему НЕ write-through:

* обновления статусов заказов происходят часто
* запись в Redis при каждом обновлении → увеличивает нагрузку
* есть риск расхождения с RabbitMQ-ивентами

Почему НЕ refresh-ahead:

* заказы меняются нерегулярно
* нет смысла обновлять кеш заранее
* такие ключи будут только расходовать ресурсы Redis

**Cache-Aside идеально ложится в сценарии, где MES и CRM перегружены чтением.**

### Write-Through (для справочных данных)

Где использовать:

* справочники (материалы, шаблоны, настройки)
* данные, меняющиеся через административную панель

Почему выбрать:

* данные редко обновляются
* при обновлении админ пишет в БД => система автоматически пишет в Redis
* кеш и БД всегда синхронизированы
* гарантированно нет старого кеша

Почему НЕ Cache-Aside:

* операторские CRUD-операции менее критичны
* важнее гарантировать свежесть данных

Почему НЕ refresh-ahead:

* бессмысленно прогревать кеш, если данные меняются очень редко

### Refresh-Ahead (ключевой для расчёта стоимости)

Это самый важный элемент.

Где использовать:

* MES — результаты расчёта 3D-моделей

Почему:

* расчёт может длиться **до 30 минут**
* при повторных запросах нужно возвращать кеш
* заранее обновлять кеш по TTL намного дешевле, чем пересчитывать
* ожидаем высокую нагрузку на этот endpoint со стороны B2B API

Пример работы:

* ключ хранится 48 часов
* TTL подходит к концу → Redis запускает «прогрев» ключа
* MES заранее инициирует фоновый расчёт
* если расчёт занимает 10–30 минут — это всё равно лучше, чем делать его по запросу клиента

Почему НЕ Cache-Aside:

* Cache-Aside вернёт старый кеш, а расчёт запустится только после запроса
* при высокой нагрузке B2B API => API будет зависать и ждать расчёта
* Cache-Aside не подходит, когда *хочется избегать cold-cache состояния*

Почему НЕ Write-Through:

* write-through предполагает, что мы записываем в кеш сразу при записи в БД
* но здесь мы не пишем в БД — мы получаем данные от MES
* паттерн неприменим

**Refresh-Ahead — оптимальный выбор для тяжёлых вычислений.**

### Итоговая стратегия кеширования в Александрит

| Зона системы                   | Что кешируем          | Паттерн       | Почему                     |
| ------------------------------ | --------------------- | ------------- | -------------------------- |
| MES — расчёт стоимости         | price result          | Refresh-Ahead | избегаем 30-мин расчётов   |
| MES — список заказов оператора | последние N заказов   | Cache-Aside   | часто читают, редко меняют |
| CRM — справочники              | материалы, тарифы     | Write-Through | малое число обновлений     |
| Shop API                       | справочники, каталоги | Cache-Aside   | разгрузка БД               |
| 3D-модели                      | файлы                 | reverse-proxy | уменьшение нагрузки на S3  |

## Предлагаемое решение

[Диаграмма последовательности действий](./sequence_diagram.drawio)

**Выбранная стратегия инвалидации кеша: программная (explicit invalidation)**

Это означает:

* После **каждого изменения заказа** (статуса, состава, оплаты, отмены)
  → Shop API **сам удаляет или обновляет кеш по ключу**.

Пример:

```
Key: orders:list
Key: order:{order_id}
```

При изменении любого заказа система вызывает:

```text
DEL orders:list
DEL order:{order_id}
```

или выполняет обновление содержимого свежими данными.

### Почему программная инвалидация лучше всего подходит

**Заказы — критически важные данные, которые должны быть актуальными**

Любая задержка в обновлении заказа (статус оплаты, подтверждение сборки, отправка курьеру)
может приводить к:

* зависшим заказам
* ошибкам в CRM / MES
* невозможности узнать реальное состояние заказа
* потере доверия пользователей

Поэтому нельзя использовать стратегии, которые допускают задержки обновления.

Программная инвалидация обеспечивает **мгновенную актуальность**.


### Ключи кеша для заказов легко определить и локализовать

Структура данных хорошо определяется паттернами:

* `order:{id}`
* `orders:list`
* `orders:user:{user_id}`

Их просто инвалидировать вручную.


### Сравнительный анализ

| Стратегия                            | Подходит?             | Почему                                       |
| ------------------------------------ | --------------------- | -------------------------------------------- |
| **Программная инвалидация по ключу** | ✅ Отлично             | Мгновенное обновление, контроль точек записи |
| TTL                                  | ⚠️ Только ограниченно | Подойдёт для списков, не для статусов        |
| Pattern-based                        | ❌ Нет                 | Слишком грубо и опасно                       |
| Refresh-Ahead                        | ❌ Нет                 | Не предсказывает обновления                  |
| Write-Through                        | ❌ Нет                 | Неестественная модель для заказов            |
| Write-Behind                         | ❌ Абсолютно нет       | Риск потери заказов                          |
